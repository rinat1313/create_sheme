# Приём ТЗ (этап 1)

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow.

## Когда включать

При **любом** получении ТЗ. `lead` читает этот skill на этапе **1**, **до** вызова `архитектор` и `дизайнер`.

Не основной сценарий для этапов 2–8: там вход — пакет этого skill.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — только этап получения ТЗ.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Специалистов этапа 2 направлять **после** пакета. Без пакета — не звать.
4. Skills `ui-ux` и `user-docs` — позже, внутри своих этапов, не вместо приёма ТЗ.

## Действия lead

1. Предварительная оценка: цель, scope, затрагивает ли продукт / UI / docs / skills.
2. Проверить, вся ли информация в доступе: вложения, ссылки, файлы в репо, внешние документы.
3. Если ТЗ про документацию — проверить, есть ли эти ресурсы в доступе (пути, файлы, ссылки). Нет доступа — вопрос пользователю. Не выдумывать содержимое недоступных документов.
4. Уточняющие вопросы пользователю — только если без них нельзя стартовать: полнота ТЗ, доступ к материалам, толкование формулировок. **Не** спрашивать, как реализовывать (это этап 2).
5. Каждый вопрос: краткая формулировка + примеры вариантов на выбор + явно «или свой вариант».
6. После операций — пакет (бриф) для передачи другим: исходное ТЗ, ответы и допущения, что есть в доступе, чего нет. Если вопросов не было — в пакете N/A.

Один круг вопросов. При молчании — зафиксировать допущения в пакете и идти дальше.

## Формат пакета

Короткие секции:

- цель;
- входы (исходное ТЗ);
- доступные ресурсы;
- пробелы (чего нет в доступе);
- ответы пользователя (или N/A);
- допущения;
- кому передавать (этап 2 и далее).

## Стоп-лист

- Не выбор API, UI, архитектуры.
- Не звать специалистов до пакета.
- Не подменять этап 2 (skill `tz-questions`).
- Не кодить до этапа 4.
- Не второй workflow вместо `tz-workflow`.

## Антипаттерны

- Второй workflow вместо `tz-workflow`.
- Вопросы «как лучше сделать» на этапе 1.
- Вызов архитектора/дизайнера до пакета.
- Выдуманное содержимое недоступных docs.
- Вопросы без вариантов и без «свой вариант».
- Повтор на этапе 2 вопросов про полноту и доступ.
