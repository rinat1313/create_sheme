# Подготовка вопросов (этап 2)

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow.

## Когда включать

После пакета этапа 1 (`tz-intake`). Группа специалистов (`архитектор`, `дизайнер`; при UI — skill `ui-ux` внутри оценки дизайнера) читает этот skill **до** этапа 3.

Не основной сценарий для этапов 1 и 3–8: вход — пакет `tz-intake`; выход — информационный файл этого skill.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — только этап подготовки вопросов.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Этап 3 начинать **после** информационного файла. Без него — не переходить к решениям.
4. Skills `ui-ux` и `user-docs` — внутри своих этапов, не вместо вопросов.
5. Полноту ТЗ и доступ к материалам не переспрашивать: это этап 1.

## Действия специалистов

1. Взять пакет этапа 1: ТЗ, ответы пользователя, доступ, допущения.
2. Проанализировать **только в своей компетенции** (архитектор — API/данные/границы; дизайнер — UI/UX).
3. На критические моменты, без которых нельзя выбрать решение, составить вопросы пользователю. Каждый вопрос: формулировка + варианты + «или свой вариант». Не спрашивать про полноту и доступ.
4. Если критических вопросов нет — явно сообщить lead: **вопросов нет**.
5. Передать lead **выводы и вопросы** (или «вопросов нет»). Пользователю не писать. Не кодить.

## Действия lead

1. Собрать выводы и вопросы всех специалистов.
2. Если у всех «вопросов нет» и противоречий в выводах нет — информационный файл с N/A по вопросам, сразу этап 3.
3. Найти пересечения: одни и те же темы в вопросах или выводах. Если ответы/вопросы **пересекаются и противоречат** — собрать только тех специалистов, чьи позиции конфликтуют. Они решают, что лучше. Пользователю не тащить внутренний спор.
4. После сверки задать пользователю оставшиеся вопросы (один круг). При молчании — допущения.
5. Если после сверки нужны ещё вопросы пользователю — задаёт только lead, с вариантами и «свой вариант».
6. Когда противоречий нет — составить **информационный файл** для этапа 3. Файл — артефакт хода (в промпте), не коммит в репозиторий.

## Формат информационного файла

Короткие секции:

- вход (пакет этапа 1);
- выводы специалистов;
- вопросы, которые были (или N/A);
- пересечения и как сняты противоречия (или N/A);
- ответы пользователя / допущения;
- кому передавать (этап 3).

## Стоп-лист

- Не повторять этап 1 (полнота, доступ).
- Не подменять этап 3 (готовые решения вместо вопросов).
- Не кодить до этапа 4.
- Не задавать вопросы пользователю мимо lead.
- Не второй workflow вместо `tz-workflow`.
- Не коммитить бриф/файл этапа в git.

## Антипаттерны

- Второй workflow вместо `tz-workflow`.
- Вопросы про полноту ТЗ и доступ на этапе 2.
- Специалист пишет пользователю напрямую.
- Lead игнорирует противоречия и не собирает авторов.
- Переход к решениям без информационного файла.
- Коммит пакета этапа в `main`.
