# Технические писатели

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow. Это **не** subagent: файлов в `.cursor/agents/` для этой роли нет. `lead` сам проходит линзу группы на этапе документации.

## Когда включать

Lead читает этот skill на этапе **4** (отдельная задача зоны документации) и на этапе **7** (`tz-docs`, тексты, схемы, help). На этапах 1–3 линза не выбирает продукт вместо `tz-specialists`. На этапах 5–6 не пишет код и не правит продукт «заодно». На этапе 8 не подменяет отчёт.

Не основной сценарий для закрытия ТЗ: выход — актуальные руководство, help и схемы для пользователя (или N/A), не отдельный workflow.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — группа линз документации внутри этапов 4 и 7.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Единственный subagent — `lead`. Не создавать и не вызывать агентов «технический писатель», «tech-writer», «docs-writer».
4. Этап документации — `tz-docs`. Стиль слоёв — `user-docs`. Линза не заменяет эти skills.
5. На этапе 7 код приложения, CSS, API, БД и тесты **не** правят. Нет пользовательских изменений — N/A, не выдумывать разделы.

## Группа

| Роль | Что делает | Когда N/A |
|------|------------|-----------|
| Технический писатель | Описывает функционал простым языком; переводит термины; схемы и презентации для пользователя; состав руководства и help | Нет пользовательского поведения, help и руководства не затрагиваются — N/A |

Линза обязательна к проходу на этапе 7, если в пуле есть задача на тексты. Нет зоны документации — N/A, не пропуск этапа 7 без пометки.

## Линзы

### Технический писатель

1. Пишет описание функционала так, как его видит обычный пользователь: что нажать, что произойдёт, какие ограничения.
2. Переводит сложные технические термины в простой вариант. Без внутренних имён API, пакетов, таблиц БД, названий skills.
3. Рисует схемы и короткие презентационные блоки для конечного пользователя (mermaid или ASCII), когда порядок действий или связи экранов неочевидны.
4. Знает, что должно быть в руководстве (сценарии, ограничения, схемы) и в help (сжатое оглавление, те же названия кнопок). Help правят только если он есть и затронут.
5. Не смешивать задачу на тексты с задачей на код. Не чинить продукт, чтобы текст «сошёлся».

## Действия lead

1. На этапе 4 (`tz-tasks`): отдельная задача зоны документации с ролью технического писателя, если меняются визуал, логика или сценарии. Нет пользовательских изменений — не назначать роль.
2. На этапе 7 (`tz-docs`): включить линзу; писать по пакету этапа 6 и фактическому UI, не по самоотчёту этапа 5.
3. Help и руководство — одни названия. Схемы — если без них сценарий непонятен.
4. Несколько слоёв (гайд, help, схема) — lead проходит их по очереди, без вызова агентов.

Выводы роли — в пакет этапа 7 (короткие пункты или N/A), не отдельные файлы «отчёта писателя» в git.

## Стоп-лист

- Не subagent и не Task на эту роль.
- Не второй workflow вместо `tz-workflow`.
- Не писать docs на этапе 6 и не кодить на этапе 7.
- Не пропускать назначенную роль без N/A.
- Не подменять `tz-docs` и `user-docs`.
- Не создавать `.cursor/agents/` для технического писателя.

## Антипаттерны

- Восстановлен агент `tech-writer` / `technical-writer`.
- Тексты на жаргоне реализации.
- Help копирует всё руководство в модалку.
- Схемы «для разработчика» вместо пользователя.
- Документация «заодно» в задаче на код.
