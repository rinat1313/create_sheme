# Специалисты

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow. Это **не** subagent: файлов в `.cursor/agents/` для этих ролей нет. `lead` сам проходит линзы группы.

## Когда включать

Lead читает этот skill на этапах **1–4** (оценка ТЗ, вопросы, решения, нарезка задач) и при **пересмотре решения** (порог 10 из `tz-verify`, слом набора на этапах 4–5). На этапах 5–8 линзы не заменяют код, прогон, docs и отчёт.

Не основной сценарий для закрытия ТЗ: выход — выводы по ролям (или N/A), не код.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — группа линз внутри этапов.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Единственный subagent — `lead`. Не создавать и не вызывать агентов «аналитик», «архитектор», «дизайнер», «ИБ», «алгоритмист», «программист», «специалист по БД».
4. Вопросы пользователю задаёт только lead (этапы 1–2). Специалистские выводы пользователю не тащить сырьём.
5. UI-линза опирается на skill `ui-ux`, не вместо него.

## Группа

| Роль | Что смотрит | Когда N/A |
|------|-------------|-----------|
| Аналитик | Соответствие ТЗ приложению; направление развития; сложность задач | ТЗ не про продукт (чисто внутренний конфиг без влияния на направление) — кратко N/A |
| Архитектор | Архитектура, внедрение технологий, границы сервисов и данных | Нет изменений API/данных/слоёв — N/A |
| UI/UX дизайнер | Современный стиль, паттерны оформления, skill `ui-ux` | Нет frontend/UI — N/A |
| Специалист по ИБ | Утечки, поверхность атаки, доступ к данным и секретам | Нет данных, сети, файлов, auth — N/A с явной пометкой |
| Алгоритмист | Математика, алгоритмы, вероятность, физика моделей | Нет расчётов, графов, геометрии, вероятностей — N/A |
| Специалист по программированию | Написание кода, теория, паттерны разработки | Нет изменений кода приложения — N/A |
| Специалист по базам хранения данных | Базы данных, оптимизация и ускорение работы хранилища | Нет хранения, запросов, индексов, схемы БД — N/A |

Все семь линз обязательны к проходу. Пропуск роли без N/A запрещён.

## Линзы

### Аналитик

1. ТЗ стыкуется с текущим приложением или тянет в сторону, которой в продукте нет.
2. Направление: усиление существующего сценария / новый контур / внутренний процесс.
3. Сложность: узкая правка, зона, сквозной контур. Не оценка в днях.

### Архитектор

1. Слои: API, данные, фронт, конфиг. Что уже есть, что нельзя ломать.
2. Новая технология — только если закрывает пробел текущего стека (Go, HTML/CSS/JS, PostgreSQL). Не внедрять «потому что ново».
3. Границы схем: на фронт только запрошенная схема.

### UI/UX дизайнер

1. Читай `ui-ux`. Паттерны: иерархия, состояния, подписи, модалки, холст, инспектор.
2. Современный стиль без ломки существующих контролов и справки.
3. Нет UI — N/A, не выдумывать экраны.

### Специалист по информационной безопасности

1. Утечки: секреты, полный dump схем, лишние данные на фронт, логи с чувствительным содержимым.
2. Поверхность: загрузка файлов, выгрузка, доступ к чужим схемам, обход ограничений.
3. Не писать эксплойты. Фиксировать риск и контрмеру в решении.

### Алгоритмист

1. Корректность расчётов, раскладки, пересечений, вероятностных и физических моделей, если они в ТЗ.
2. Сложность алгоритма относительно объёма схем, не микрооптимизация без нужды.
3. Нет математики в ТЗ — N/A.

### Специалист по программированию

1. Как писать код: читаемость, границы модулей, теория и паттерны разработки (не ради паттерна).
2. Стык с уже принятым стилем проекта: Go, HTML/CSS/JS, без лишних абстракций.
3. Нет кода приложения — N/A. Не подменять этап 5 и не писать реализацию из линзы.

### Специалист по базам хранения данных

1. Модель хранения, запросы, индексы, нагрузка чтения/записи.
2. Оптимизация и ускорение без ломки целостности и без лишней денормализации.
3. Нет БД и хранилища в ТЗ — N/A. Не менять схему «на всякий случай».

## Действия lead

1. На этапе 1 (`tz-intake`): аналитик — соответствие, направление, грубая сложность; остальные — только если без линзы нельзя понять полноту ТЗ. Не выбирать архитектуру на этапе 1.
2. На этапе 2 (`tz-questions`): все семь линз; критические вопросы или «вопросов нет» по роли.
3. На этапе 3 (`tz-solutions`): решения с учётом всех неприменённых-как-N/A линз; сверка противоречий между ролями (два прохода).
4. На этапе 4 (`tz-tasks`): аналитик — сложность нарезки; архитектор — зоны; дизайнер/ИБ/алгоритмист/программист/БД — если зона есть в пуле.
5. Порог 10 (`tz-verify`) или слом набора: заново все семь линз по спорному решению, затем этап 3.

Выводы ролей — в пакет этапа (короткие пункты или N/A), не отдельные файлы в git.

## Стоп-лист

- Не subagent и не Task на эти роли.
- Не второй workflow вместо `tz-workflow`.
- Не кодить из линз до финального пула этапа 4.
- Не пропускать роль без N/A.
- Не отдавать пользователю внутренний спор линз: сводит lead.

## Антипаттерны

- Восстановлены файлы агентов архитектора или дизайнера.
- ИБ пропущен, потому что «это же внутренний инструмент».
- Алгоритмист пишет формулы там, где ТЗ про кнопку.
- Аналитик оценивает календарные сроки.
- Программист навязывает паттерн без нужды в коде.
- Специалист по БД предлагает индексы и смену схемы без запросов и хранения.
