# Подготовка задач (этап 4)

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow.

## Когда включать

После пакета этапа 3 (`tz-solutions`). `lead` и `архитектор` читают этот skill **до** этапа 5. Исполнители (`worker`; при UI в наборе — `дизайнер`) читают его, когда разбирают черновой пул.

Не основной сценарий для этапов 1–3 и 5–8: вход — пакет для пула задач; выход — финальный пул исполнителям.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — только этап подготовки задач.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Этап 5 (`tz-execute`) начинать **после** финального пула. Без него — не кодить.
4. Skills `ui-ux` и `user-docs` — внутри своих этапов, не вместо пула.
5. Новые вопросы пользователю здесь не задавать: это этап 2. Если без вопроса пользователя нельзя выбрать нарезку — lead возвращает на этап 2, не опрос из `tz-tasks`.

## Действия lead и архитектора (черновик)

1. Взять **полученную информацию**: пакет этапа 3 (согласованный набор решений, снятые пересечения, N/A).
2. Вместе создать **черновой пул задач**, разделённый **по зонам разработки** (роли/компетенции: код, архитектура/данные, UI, документация). Задача без зоны и без трассировки к решению набора — не класть.
3. Lead владеет сборкой пула. Архитектор сверяет зоны, границы и соответствие набору этапа 3. Lead не подменяет принятые решения новыми «от себя».
4. Черновик отдать на анализ архитектору и исполнителям зон. Не вызывать тестировщиков и технического писателя как авторов пула.

## Действия архитектора и исполнителей (анализ)

1. Разобрать черновой пул **только в своей зоне**.
2. Собрать **пул вопросов к lead и архитектору**: неясная нарезка, риск сломать принятое решение, нехватка зоны, пересечение задач. Вопросы внутренние. Пользователю не писать. Не кодить.
3. Если вопросов нет — явно сообщить lead: **вопросов нет**.
4. Worker на этом этапе — разбор пула, не реализация.

## Решение: реализовать или изменить

1. Lead с архитектором разбирают пул вопросов.
2. Если набор этапа 3 можно сохранить — **реализуем** принятые решения: правка формулировок, порядка, N/A по роли. Повторная сверка черновика.
3. Если нужно **изменить решение** — подключить специалистов своей зоны для другого решения. Новое решение **не должно противоречить уже принятым**. Lead проверяет стык с набором этапа 3.
4. Уточнение, которое **не ломает** согласованный набор — остаётся на этапе 4, повтор анализа.
5. Изменение, которое **ломает** набор (другая граница, отказ от принятого, решение вне пакета 3) — **возврат на этап 3** (`tz-solutions`), не тихая перепись пула и не этап 1.
6. После любого изменения пула или решения — ещё раз проверить противоречия. Пока конфликт или открытые внутренние вопросы — не этап 5.

## Финальный пул

Когда противоречий нет и проверка создания пула успешна — lead фиксирует **пул задач для исполнителей** и передаёт на этап 5. Пул — артефакт хода (в промпте), не коммит в репозиторий.

## Формат пула задач

Короткие секции:

- вход (пакет этапа 3);
- пул по зонам;
- трассировка задача → решение набора;
- внутренние вопросы и как сняты (или N/A);
- реализовать набор / правка внутри 4 / возврат на этап 3;
- кому передавать (этап 5).

## Стоп-лист

- Не повторять этап 1 (полнота, доступ), этап 2 (опрос пользователя), этап 3 (новые решения без сверки).
- Не кодить до финального пула.
- Не задавать вопросы пользователю мимо lead.
- Не принимать решение, которое противоречит уже принятым.
- Не второй workflow вместо `tz-workflow`.
- Не коммитить пул этапа в git.

## Антипаттерны

- Второй workflow вместо `tz-workflow`.
- Пул из воздуха, без пакета этапа 3.
- Lead один режет задачи без архитектора.
- Исполнители не разбирают черновик и сразу кодят.
- Тихая смена решения, которая ломает набор этапа 3.
- Новое решение без проверки на противоречие принятому.
- Вызов worker на черновике до финальной проверки пула.
- Коммит пакета этапа в `main`.
