# Тестировщики

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow. Это **не** subagent: файлов в `.cursor/agents/` для этих ролей нет. `lead` сам проходит линзы группы на этапе проверки.

## Когда включать

Lead читает этот skill на этапе **4** (пометки зон проверки в пуле) и на этапе **6** (`tz-verify`, прогон). На этапах 1–3 и 5 линзы не заменяют проектирование и код. На этапах 7–8 не пишут docs и отчёт.

Не основной сценарий для закрытия ТЗ: выход — факты прогона и пакет этапа 6, не отдельный workflow.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — группа линз проверки внутри этапов 4 и 6.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Единственный subagent — `lead`. Не создавать и не вызывать агентов «QA», «manual», «sql-тестировщик», «тестировщик», «ui-tester».
4. Прогон — `tz-verify`. Тестировщики не чинят продукт: код приложения, конфигурацию, help и руководство **не** правят. Неуспех — разбор в `tz-verify`, переделка на этапе 5.
5. Frontend-линза опирается на skill `ui-ux` (ручной прогон UI), не вместо него. Исполнение кода — `tz-executors`, не эта группа.

## Группа

| Роль | Что делает | Когда N/A |
|------|------------|-----------|
| QA тестировщик | Тестирует код продукта; пишет автотесты и тесты конкретных функций | Нет кода приложения для проверки — N/A |
| Manual тестировщик | Тестирует приложение вручную (сценарии, UI, клики и ввод) | Нет запускаемого UI/клиента — N/A |
| SQL тестировщик | Проверяет работу баз данных и SQL-запросов | Нет БД, миграций, SQL — N/A |

Все три линзы обязательны к проходу на этапе 6, если задача в пуле. Нет зоны проверки — N/A по роли, не пропуск всей группы.

## Линзы

### QA тестировщик

1. Проверяет код продукта: сценарии функций, границы, регрессии автотестами.
2. Пишет автотесты и тесты конкретных функций как артефакт проверки, не как правку продукта.
3. Во время прогона не чинит реализацию. Падение теста — дефект в пакет этапа 6, не «починить заодно».

### Manual тестировщик

1. Прогоняет приложение вручную: сценарии пользователя, ошибки, пустые состояния.
2. При UI — клики и ввод, не один скриншот (`ui-ux`).
3. Нет клиента — N/A, не выдумывать экраны.

### SQL тестировщик

1. Проверяет работу БД: запросы, целостность, миграции, фактический результат данных.
2. Не менять схему и данные «чтобы тест прошёл».
3. Стык с SQL-исполнителем: исполнитель пишет запросы, эта линза проверяет факт.

## Действия lead

1. На этапе 4 (`tz-tasks`): у задачи зоны проверки — QA / manual / SQL (можно несколько). Нет зоны — не назначать роль.
2. На этапе 6 (`tz-verify`): включить назначенные линзы; чужие зоны не гонять без причины.
3. Во время прогона не править код продукта и документацию. Автотесты QA не подменяют починку.
4. Несколько ролей — lead проходит каждую по очереди, без вызова агентов.

Выводы ролей — в пакет этапа 6 (короткие пункты или N/A), не отдельные файлы в git.

## Стоп-лист

- Не subagent и не Task на эти роли.
- Не второй workflow вместо `tz-workflow`.
- Не чинить продукт на прогоне.
- Не пропускать назначенную роль без N/A.
- Не подменять этап 5 и `tz-executors`.
- Не создавать `.cursor/agents/` для тестировщиков.

## Антипаттерны

- Восстановлены агенты `tester` / `ui-tester`.
- QA правит реализацию, чтобы автотест стал зелёным.
- Manual объявляет UI пройденным по скриншоту.
- SQL меняет схему или фикстуры «на всякий случай».
- Прогон заменён локальной проверкой этапа 5.
