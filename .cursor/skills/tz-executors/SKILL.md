# Исполнители

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow. Это **не** subagent: файлов в `.cursor/agents/` для этих ролей нет. `lead` сам проходит линзы группы на этапе выполнения.

## Когда включать

Lead читает этот skill на этапе **4** (нарезка пула по зонам исполнения) и на этапе **5** (`tz-execute`, код по зоне). На этапах 1–3 линзы не выбирают архитектуру вместо `tz-specialists`. На этапах 6–8 линзы не заменяют прогон, docs и отчёт.

Не основной сценарий для закрытия ТЗ: выход — реализация по зоне и пометки N/A, не отдельный workflow.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — группа линз исполнения внутри этапов 4–5.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Единственный subagent — `lead`. Не создавать и не вызывать агентов «backend», «frontend», «sql», «devops», «worker».
4. Проектирование — `tz-specialists`. Исполнители не пересматривают набор решений этапа 3. Слом набора — возврат на этап 3, не «другой паттерн из линзы».
5. Frontend-линза опирается на skill `ui-ux`, не вместо него. Backend-линза — на `go-logging` при новых рабочих функциях Go.

## Группа

| Роль | Что делает | Когда N/A |
|------|------------|-----------|
| Backend программист | Бэкенд на основном языке проекта (Go); паттерны без лишних абстракций | Нет серверного кода, API, сервисов — N/A |
| Frontend программист | Фронтенд на основном стеке (HTML/CSS/JS); паттерны UI-кода | Нет UI/клиента — N/A |
| SQL программист | Функционал и скрипты СУБД, миграции, запросы, данные | Нет БД, миграций, SQL — N/A |
| DevOps | Конфиги, скрипты развёртывания, Docker | Нет деплоя, контейнеров, инфраструктуры — N/A |

Все четыре линзы обязательны к проходу на этапе 5, если задача в пуле. Нет зоны в задаче — N/A по роли, не пропуск всей группы.

## Линзы

### Backend программист

1. Пишет серверный код на Go: API, сервисы, границы пакетов.
2. Паттерны — по нужде проекта, не ради паттерна.
3. Логирование рабочих функций — skill `go-logging`. Комментарии в коде не добавлять.

### Frontend программист

1. Пишет клиент на HTML/CSS/JS: холст, инспектор, меню, модалки.
2. Паттерны UI-кода и skill `ui-ux`. Не ломать существующие контролы и справку «заодно».
3. На фронт только запрошенная схема. Help продукта — только если задача есть в пуле (этап 7).

### SQL программист

1. Скрипты СУБД, миграции данных, запросы, целостность.
2. Не менять схему «на всякий случай». Оптимизация — если есть запросы и нагрузка.
3. Стык с линзой БД из `tz-specialists`: специалисты задают модель, SQL реализует принятое.

### DevOps

1. Конфигурации, скрипты развёртывания, Docker.
2. Не усложнять пайплайн без задачи в пуле. Секреты не класть в git и в образ.
3. Нет деплоя в ТЗ — N/A.

## Действия lead

1. На этапе 4 (`tz-tasks`): у каждой задачи зоны исполнения — backend / frontend / SQL / DevOps (можно несколько). Нет зоны — не назначать роль.
2. На этапе 5 (`tz-execute`): для задачи включить только назначенные линзы; чужие зоны не трогать.
3. Локальная проверка — в рамках своей зоны задачи, не этап 6.
4. Несколько ролей в одной задаче — lead проходит каждую по очереди, без вызова агентов.

Выводы ролей — в отчёт этапа 5 (короткие пункты или N/A), не отдельные файлы в git.

## Стоп-лист

- Не subagent и не Task на эти роли.
- Не второй workflow вместо `tz-workflow`.
- Не кодить до финального пула этапа 4.
- Не пропускать назначенную роль без N/A.
- Не подменять `tz-specialists` на этапах 1–3.
- Не создавать `.cursor/agents/` для исполнителей.

## Антипаттерны

- Восстановлен файл агента `worker` или отдельные агенты backend/frontend.
- Frontend пишет API, backend правит CSS без задачи в пуле.
- SQL навязывает миграцию без хранения в ТЗ.
- DevOps добавляет Docker «на будущее».
- Исполнитель меняет принятое решение этапа 3 из паттерна.
