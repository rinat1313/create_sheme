# Рабочий процесс выполнения ТЗ

При получении тз lead должен получить обратную связь от специалистов по этому тз, составить список задач для исполнителей, после исполнения отдать на проверку и тестирование, по результатам тестирования и обратной связи принять решение о переделки или завершении работы по ТЗ.

## Обязательность

При **любом** получении ТЗ от пользователя workflow **обязателен полностью**. Пропуск этапов или специалистов запрещён.

### Обязательная цепочка

1. **lead** — первичная оценка ТЗ, план работ, финальный отчёт.
2. **архитектор** — оценка архитектуры, БД, API (если затронут backend или структура данных).
3. **дизайнер** — оценка UI/UX (если затронут frontend или отображение).
4. **worker** — реализация кода.
5. **тестировщик** — проверка результата без правок кода.
6. **тестировщик UI интерфейса** — проверка UI, отрисовки и условий отображения без правок кода (обязателен при frontend/UI-изменениях).

Специалисты вызываются через Task tool **до начала реализации**. Если ТЗ затрагивает только backend — дизайнер даёт краткую оценку или подтверждает «не требуется». Если только правила/skills — worker выполняет правки, тестировщик проверяет. При UI-изменениях дополнительно вызывается тестировщик UI интерфейса. При frontend/UI читай skill `ui-ux` (`.cursor/skills/ui-ux/SKILL.md`) на этапах дизайнер, worker и тестировщик UI интерфейса; skill дополняет этот workflow и не меняет обязательную цепочку.

### Запрещено

- Выполнять ТЗ без чтения этого skill.
- Пропускать lead, worker и тестировщик.
- Пропускать архитектор/дизайнер без явного обоснования в отчёте lead.
- Считать задачу завершённой до отчёта lead и проверки тестировщиком.

## Участники

| Роль | Subagent | Ответственность |
|------|----------|-----------------|
| Lead | `lead` | Координация, план работ, отчёт, завершение |
| Worker | `worker` | Код на Go, HTML, CSS, JS, PostgreSQL |
| Тестировщик | `тестировщик` | Тестирование без правок кода |
| Тестировщик UI | `тестировщик UI интерфейса` | Тестирование UI, отрисовки и условий отображения без правок кода |
| Дизайнер | `дизайнер` | Дизайн, отрисовка, проверка результата |
| Архитектор | `архитектор` | Архитектура микросервиса, страниц и СУБД |

## Этапы

### 1. Получение ТЗ

1. Получи ТЗ от пользователя.
2. Делегируй `lead` первичную оценку ТЗ.
3. `lead` направляет ТЗ специалистам: `архитектор`, `дизайнер`.

### 2. Сбор обратной связи

1. `архитектор` проектирует архитектуру микросервиса, страниц и СУБД.
2. `дизайнер` анализирует ТЗ и формирует рекомендации по дизайну.
3. `lead` собирает обратную связь от всех специалистов.

### 3. Планирование

1. `lead` составляет список задач для исполнителей.
2. Задачи на разработку передаются `worker`.
3. Задачи на дизайн передаются `дизайнер` для рекомендаций, реализацию выполняет `worker`.

### 4. Разработка

1. `worker` пишет код на Go, HTML, CSS, JS.
2. `worker` работает с PostgreSQL.
3. Каждая функция логируется с управляемым уровнем логирования.
4. Комментарии в коде не используются.

### 5. Проверка и тестирование

1. `lead` передаёт результат `тестировщик` для проверки.
2. `тестировщик` не вносит изменения в код.
3. При UI-изменениях `lead` передаёт результат `тестировщик UI интерфейса` для проверки отрисовки и условий отображения.
4. `тестировщик UI интерфейса` не вносит изменения в код.
5. `lead` собирает обратную связь от `архитектор`, `дизайнер`, `тестировщик` и при необходимости `тестировщик UI интерфейса`.

### 6. Решение о доработке или завершении

1. По результатам тестирования и обратной связи `lead` принимает решение о переделке или завершении работы по ТЗ.
2. Если требуются доработки — `lead` добавляет задачи `worker` и повторяет этапы разработки и тестирования.
3. Если результат удовлетворительный — переход к завершению.

### 7. Завершение

1. `lead` формирует отчёт о проделанной работе.
2. После положительного прохождения тестирования и проверки:
   - изменения коммитятся и пушатся в feature-ветку;
   - **обязательно** выполняется слияние в `main` и push `origin/main`.

3. Порядок действий:
   - `git checkout main && git pull origin main`
   - `git merge <feature-branch>`
   - `git push origin main`
   - проверить, что `main` содержит все изменения задачи

4. Задача не считается завершённой, пока изменения не попали в `main`.

## Отчёт lead

Отчёт должен содержать:

- что сделано;
- что не сделано;
- выявленные риски;
- предложения по улучшению.
