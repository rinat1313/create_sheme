# Рабочий процесс выполнения ТЗ

Это основной skill при получении ТЗ. Этапы 1–7 детализированы skills `tz-intake`, `tz-questions`, `tz-solutions`, `tz-tasks`, `tz-execute`, `tz-verify` и `tz-docs`. Этап 8 пока каркас: не выдумывай толстые регламенты внутри него.

Актуальная копия этого skill и остальных `.cursor/skills` — ветка `origin/main` (правило `cursor-config-on-main`). Перед этапами `git fetch origin main` и читай файлы с `origin/main`, если локальный snapshot старше.

Дополнения (не заменяют эту цепочку): `tz-intake` на этапе 1; `tz-questions` на этапе 2; `tz-solutions` на этапе 3; `tz-tasks` на этапе 4; `tz-execute` на этапе 5; `tz-verify` на этапе 6; `tz-docs` на этапе 7; `ui-ux` при frontend/UI; `user-docs` — стиль слоёв внутри этапа 7.

## Обязательная цепочка

1. Получение ТЗ.
2. Подготовка вопросов.
3. Подготовка решений.
4. Подготовка задач.
5. Выполнение задач.
6. Проверка выполненной работы.
7. Подготовка документации.
8. Подготовка отчетов.

Пропуск этапов запрещён. Если этап не применим (нет вопросов, нет UI, нет пользовательского поведения), lead явно пишет N/A и почему, затем идёт дальше. Не ждать пользователя бесконечно: один круг вопросов, при молчании — зафиксировать допущения.

## Участники

| Роль | Subagent | Где в цепочке |
|------|----------|----------------|
| Lead | `lead` | Этапы 1–8; координация всех; на этапе 6 — `tz-verify`; на этапе 7 — `tz-docs` |
| Архитектор | `архитектор` | Вопросы и решения до задач; на этапе 6 — анализ решения после 10 неуспехов |
| Дизайнер | `дизайнер` | Вопросы и решения по UI до задач |
| Worker | `worker` | Выполнение задач (этап 5, `tz-execute`) |
| Тестировщик | `тестировщик` | Проверка (этап 6, `tz-verify`) |
| Тестировщик UI | `тестировщик UI интерфейса` | Проверка UI при frontend (этап 6, `tz-verify`) |
| Технический писатель | `технический писатель` | Документация (этап 7, `tz-docs`) |

Специалисты вызываются через Task tool. Вопросы пользователю задаёт только `lead`. Реализацию без этапа 4 (списка задач от lead) запрещено начинать.

### Запрещено

- Выполнять ТЗ без чтения этого skill.
- Пропускать lead, worker и тестировщик.
- Пропускать архитектор/дизайнер без явного обоснования в отчёте lead.
- Считать задачу завершённой до отчёта lead (этап 8) и проверки (этап 6).
- Закрывать ТЗ с пользовательскими изменениями при устаревших help или руководстве.

## Этапы

### 1. Получение ТЗ

1. Получи ТЗ от пользователя.
2. Вызови `lead` первым.
3. `lead` читает skill `tz-intake`: предварительная оценка, проверка доступа к материалам, уточняющие вопросы только если без них нельзя стартовать (полнота, доступ, толкование ТЗ). Каждый вопрос — формулировка + варианты на выбор + «или свой вариант». Не спрашивать, как реализовывать.
4. `lead` фиксирует пакет (бриф): исходное ТЗ, ответы/допущения, что есть в доступе, чего нет. Вопросов не было — N/A в пакете.
5. Специалистов (`архитектор`, `дизайнер`; при UI — skill `ui-ux`) направлять **после** пакета.

### 2. Подготовка вопросов

1. Вход этапа — пакет этапа 1. Не повторять вопросы про полноту ТЗ и доступ к материалам.
2. Читай skill `tz-questions`: специалисты анализируют пакет в своей компетенции, критические вопросы или явный сигнал «вопросов нет», всё передают `lead`.
3. `lead` сводит выводы; при пересечении и противоречии собирает авторов, они решают что лучше; пользователю — только оставшиеся вопросы (через lead).
4. Если вопросов нет и противоречий нет — N/A, сразу этап 3.
5. Если ответа нет — `lead` фиксирует допущения и идёт дальше.
6. Без противоречий `lead` составляет информационный файл для этапа 3.

### 3. Подготовка решений

1. Вход этапа — информационный файл этапа 2 (ТЗ, вопросы, ответы).
2. Читай skill `tz-solutions`: специалисты готовят решения в своей специализации и отдают `lead`.
3. `lead` собирает решения, проверяет противоречия; при пересечении и риске собирает авторов, они пересматривают стыки и совместимость с уже принятыми решениями.
4. `lead` ещё раз проверяет все решения на противоречия.
5. Без противоречий `lead` готовит пакет для формирования пула задач (этап 4).

### 4. Подготовка задач

1. Вход этапа — пакет этапа 3. Реализацию без финального пула запрещено начинать.
2. Читай skill `tz-tasks`: `lead` и `архитектор` создают черновой пул по зонам; архитектор и исполнители анализируют пул и собирают внутренние вопросы к lead и архитектору.
3. Решают: реализовать принятый набор или изменить решение. Другое решение — через специалистов; оно не должно противоречить уже принятым. Слом набора — возврат на этап 3, не этап 1.
4. После успешной проверки — финальный пул исполнителям (код — `worker`; UI-рекомендации — `дизайнер`, реализацию делает `worker`; документация этапа 7 — если меняются визуал, логика или сценарии, иначе N/A).

### 5. Выполнение задач

1. Вход этапа — финальный пул этапа 4. Без него — не кодить.
2. Читай skill `tz-execute`: исполнители работают только в своей зоне; после задачи — локальная проверка своей реализации, не всего функционала; чужие зоны без явного указания в пуле не трогать.
3. После пула задач `worker` составляет итоговую информацию для `lead`: что сделано, какие проблемы, что не удалось решить.
4. `lead` оценивает отчёт: нет проблем — этап 6; недочёт реализации в зоне — доработка на этапе 5; слом набора решений — возврат на этап 3 (`tz-solutions`), не этап 1.
5. Если проверка (этап 6) вернула дефекты — вернуться сюда, не на этап 1.
6. При UI — skill `ui-ux`. Логирование функций, без комментариев в коде.

### 6. Проверка выполненной работы

1. Читай skill `tz-verify`. `lead` передаёт отчёт этапа 5 группе тестировщиков (`тестировщик`; при UI — ещё `тестировщик UI интерфейса`).
2. Тестировщики проверяют выполненные задачи **без** правок кода, тестов, конфигурации и документации.
3. Неуспех — информация lead на переделку: lead разбирает факт, недоделки и расхождение отчёта исполнителя с фактом; задача на этап 5 и повторную проверку.
4. Одна задача не получается более 10 раз — заново проанализировать решение этапа 3 с `архитектор` и при UI `дизайнер`; иное решение — через этап 3, не тихая правка на 6.
5. Успех всех проверок — пакет для этапа 7: сведения о работе и документы/файлы с изменениями.

### 7. Подготовка документации

1. Читай skill `tz-docs`. `lead` передаёт пакет этапа 6 группе технических писателей (`технический писатель`).
2. Писатели анализируют сведения и вносят изменения в документацию проекта. Help в UI — если он есть и затронут.
3. Информация для пользователя оформляется **отдельной задачей** (из пула этапа 4 или добавленной lead), не внутри задачи на код.
4. Тексты — простым доступным языком (стиль слоёв — `user-docs`). Нет пользовательских изменений — N/A.

### 8. Подготовка отчетов

1. `lead` формирует отчёт: что сделано; что не сделано; риски; предложения по улучшению.
2. После успешной проверки: коммит, merge в `main`, push `origin/main` (см. `commit-to-main`, `merge-to-main`).
3. Задача не завершена, пока изменения не в `main`.
4. Детали этапа — позже.
