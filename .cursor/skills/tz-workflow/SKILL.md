# Рабочий процесс выполнения ТЗ

Это основной skill при получении ТЗ. Пользователь позже детализирует каждый этап. Пока действуй по каркасу ниже, не выдумывай толстые регламенты внутри этапов.

Дополнения (не заменяют эту цепочку): `tz-intake` на этапе 1; `ui-ux` при frontend/UI; `user-docs` после пользовательских изменений.

## Обязательная цепочка

1. Получение ТЗ.
2. Подготовка вопросов.
3. Подготовка решений.
4. Подготовка задач.
5. Выполнение задач.
6. Проверка выполненной работы.
7. Подготовка документации.
8. Подготовка отчетов.

Пропуск этапов запрещён. Если этап не применим (нет вопросов, нет UI, нет пользовательского поведения), lead явно пишет N/A и почему, затем идёт дальше. Не ждать пользователя бесконечно: один круг вопросов, при молчании — зафиксировать допущения.

## Участники

| Роль | Subagent | Где в цепочке |
|------|----------|----------------|
| Lead | `lead` | Этапы 1–4 и 8; координация всех |
| Архитектор | `архитектор` | Вопросы и решения до задач; сверка на проверке |
| Дизайнер | `дизайнер` | Вопросы и решения по UI до задач |
| Worker | `worker` | Выполнение задач |
| Тестировщик | `тестировщик` | Проверка |
| Тестировщик UI | `тестировщик UI интерфейса` | Проверка UI при frontend |
| Технический писатель | `технический писатель` | Документация |

Специалисты вызываются через Task tool. Вопросы пользователю задаёт только `lead`. Реализацию без этапа 4 (списка задач от lead) запрещено начинать.

### Запрещено

- Выполнять ТЗ без чтения этого skill.
- Пропускать lead, worker и тестировщик.
- Пропускать архитектор/дизайнер без явного обоснования в отчёте lead.
- Считать задачу завершённой до отчёта lead (этап 8) и проверки (этап 6).
- Закрывать ТЗ с пользовательскими изменениями при устаревших help или руководстве.

## Этапы

### 1. Получение ТЗ

1. Получи ТЗ от пользователя.
2. Вызови `lead` первым.
3. `lead` читает skill `tz-intake`: предварительная оценка, проверка доступа к материалам, уточняющие вопросы только если без них нельзя стартовать (полнота, доступ, толкование ТЗ). Каждый вопрос — формулировка + варианты на выбор + «или свой вариант». Не спрашивать, как реализовывать.
4. `lead` фиксирует пакет (бриф): исходное ТЗ, ответы/допущения, что есть в доступе, чего нет. Вопросов не было — N/A в пакете.
5. Специалистов (`архитектор`, `дизайнер`; при UI — skill `ui-ux`) направлять **после** пакета.

### 2. Подготовка вопросов

1. Вход этапа — пакет этапа 1. Не повторять вопросы про полноту ТЗ и доступ к материалам.
2. Специалисты оценивают пакет и готовят вопросы пользователю: только то, без чего нельзя выбрать решение.
3. `lead` фильтрует список (коротко, без внутренних споров про реализацию) и задаёт вопросы пользователю.
4. Если вопросов нет — N/A, сразу этап 3.
5. Если ответа нет — `lead` фиксирует допущения и идёт дальше.
6. Детали этапа — позже.

### 3. Подготовка решений

1. После ответов (или допущений) специалисты дают лучшие предложения: архитектор — API/данные, дизайнер — UI.
2. `lead` сводит варианты, не подменяет специалистов.
3. Детали этапа — позже.

### 4. Подготовка задач

1. `lead` генерирует задачи исполнителям из выбранных предложений.
2. Задачи на код — `worker`. Рекомендации по UI — `дизайнер`, реализацию делает `worker`.
3. В план входят задачи на документацию (этап 7), если меняются визуал, логика или сценарии; иначе «документация не требуется».
4. Детали этапа — позже.

### 5. Выполнение задач

1. `worker` реализует задачи: Go, HTML, CSS, JS, PostgreSQL.
2. Логирование функций, без комментариев в коде.
3. При UI — skill `ui-ux`. Help по мере смены UI/логики не откладывать «на потом», если тексты уже известны.
4. Если проверка (этап 6) вернула дефекты — вернуться сюда, не на этап 1.
5. Детали этапа — позже.

### 6. Проверка выполненной работы

1. `тестировщик` проверяет результат без правок кода.
2. При UI — `тестировщик UI интерфейса` без правок кода.
3. При необходимости сверка с `архитектор` / `дизайнер`.
4. При провале — задачи `worker` и повтор этапов 5–6.
5. Детали этапа — позже.

### 7. Подготовка документации

1. При пользовательских изменениях — `технический писатель` и skill `user-docs`: руководство, help по необходимости.
2. Если визуал/логика не менялись — N/A, не трогать справку продукта.
3. Этап 7 — гейт «документы актуальны», не единственное место, где пишут help.
4. Детали этапа — позже.

### 8. Подготовка отчетов

1. `lead` формирует отчёт: что сделано; что не сделано; риски; предложения по улучшению.
2. После успешной проверки: коммит, merge в `main`, push `origin/main` (см. `commit-to-main`, `merge-to-main`).
3. Задача не завершена, пока изменения не в `main`.
4. Детали этапа — позже.
