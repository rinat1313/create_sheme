# Подготовка решений (этап 3)

Skill **дополняет** `tz-workflow`. Не заменяет его. Не дублирует 8 этапов и не создаёт второй workflow.

## Когда включать

После информационного файла этапа 2 (`tz-questions`). Группа специалистов (`архитектор`, `дизайнер`; при UI — skill `ui-ux` внутри специализации дизайнера) читает этот skill **до** этапа 4.

Не основной сценарий для этапов 1–2 и 4–8: вход — ТЗ, вопросы и ответы (файл этапа 2); выход — пакет для пула задач.

## Связь с tz-workflow

1. Обязательная цепочка — 8 этапов `tz-workflow`. Этот skill — только этап подготовки решений.
2. Git, коммиты и DoD — по `tz-workflow`, `commit-to-main`, `merge-to-main`.
3. Этап 4 начинать **после** пакета этого skill. Без него — не формировать задачи и не кодить.
4. Skills `ui-ux` и `user-docs` — внутри своих этапов, не вместо решений.
5. Новые вопросы пользователю здесь не задавать: это этап 2. Если без вопроса нельзя выбрать решение — lead возвращает на этап 2, не опрос из `tz-solutions`.

## Действия специалистов

1. Взять ТЗ, вопросы и ответы (информационный файл этапа 2).
2. Проанализировать **только в своей специализации** (архитектор — API/данные/границы; дизайнер — UI/UX или явный N/A).
3. Подготовить решения в своей зоне. Не список задач worker. Не код.
4. Отдать решения только `lead`. Пользователю не писать.
5. Если lead вернул стык (пересечение, риск конфликта с уже принятыми решениями) — заново рассмотреть свои решения и проверить, не возникнут ли проблемы с уже согласованным. Результат снова только lead.

## Действия lead

1. Собрать решения всех специалистов.
2. Проверить противоречия и пересечения: где решения бьются или вместе могут дать проблему.
3. При пересечении и риске — запрос **только** затронутым специалистам. Они пересматривают стыки и совместимость с уже принятыми решениями. Внутренний спор пользователю не тащить.
4. После правок **ещё раз** проверить все решения на противоречия. Пока есть конфликт — повторить шаг 3, не идти в этап 4.
5. Когда противоречий нет — подготовить **пакет для формирования пула задач** (этап 4). Пакет — артефакт хода (в промпте), не коммит в репозиторий.
6. Не подменять специалистов своими решениями. Не писать задачи worker на этом этапе.

## Формат пакета для пула задач

Короткие секции:

- вход (файл этапа 2);
- решения специалистов;
- пересечения и как сняты противоречия (или N/A);
- согласованный набор решений;
- N/A (нет UI / нет API / нет вопросов);
- кому передавать (этап 4).

## Стоп-лист

- Не повторять этап 1 (полнота, доступ) и этап 2 (опрос пользователя).
- Не подменять этап 4 (список задач worker).
- Не кодить до этапа 4.
- Не задавать вопросы пользователю мимо lead.
- Не второй workflow вместо `tz-workflow`.
- Не коммитить пакет этапа в git.

## Антипаттерны

- Второй workflow вместо `tz-workflow`.
- Новые вопросы пользователю на этапе 3 вместо возврата на этап 2.
- Lead игнорирует пересечения и не собирает авторов.
- Один проход сверки: нет повторной проверки после правок.
- Пакет решений превращён в задачи worker.
- Коммит пакета этапа в `main`.
